# Architecture Decisions

## 2026-09-26 — Source/settings extension

Add OpenAlex/Crossref through the existing provider port, without source-specific
engine branches. Source catalog and settings services replace hard-coded desktop
choices. Discovery defaults and monitoring permissions are distinct, and saved
query revisions remain explicit. UI never orchestrates ingestion or source batches.
API keys are session/environment-only, not plaintext preferences. Enrichment and
trial pipelines are reserved rather than pretending keyword discovery implements
them. Permutation tests exposed missing field ownership: migration `0005` adds
canonical-field provenance and injectable source-priority selection; old origins
are conservatively unknown. See [design](SOURCE_SETTINGS_DESIGN.md).

This log separates **approved direction** from **proposed defaults**. Proposed defaults are not implementation approvals.

| ID | Status | Decision and reason | Alternatives considered |
| --- | --- | --- | --- |
| D-001 | Approved | Use a modular monolith with a reusable Python core. It keeps deployment simple while preserving boundaries for future clients and workers. | A desktop-only codebase would tie research logic to UI; microservices add operational cost before there is a workload need. |
| D-002 | Approved | Make the desktop application a client of application services. The same services can later be called from FastAPI or workers. | Embedding provider and database logic in PySide6 screens. |
| D-003 | Approved | Implement each literature source as a provider module behind a stable interface. Source syntax and access policies remain local to the module. | Centralized source-specific conditionals throughout the engine. |
| D-004 | Approved | Preserve immutable raw API responses or source snapshots with provenance and parser version for audit and reprocessing. | Keeping only canonical fields would lose evidence for corrections and parser changes. |
| D-005 | Approved | Record domain events through a transactional outbox. Consumers for notifications, AI, ranking, and analytics may be added later. | Directly calling future services inside a search transaction, or requiring a broker in v1. |
| D-006 | Approved | Add Research Projects containing saved queries and paper associations with project-specific tags and review state. | Treating every search as a disconnected global list. |
| D-007 | Approved | Limit v1 to new-paper discovery, metadata storage, query/project management, review, and export. PDF download and AI analysis are excluded. | Starting with full-text and AI workflows would obscure the reliability of discovery and provenance. |
| D-008 | Approved recommendation | Use PubMed and Europe PMC as first medical discovery providers. Add Crossref and OpenAlex for enrichment and wider coverage. Keep ClinicalTrials.gov studies separate from publications. | Treating all sources as interchangeable article feeds. |
| D-009 | Approved design | Merge by trustworthy exact identifiers first; preserve source-specific metadata and uncertain match candidates. | Aggressive title-only deduplication can combine distinct articles. |
| D-010 | Partly implemented | Stage 1 uses a portable SQLAlchemy schema, SQLite migrations, and no UI. PostgreSQL, PySide6, FastAPI, and CSV/RIS remain later stages; export format is still a proposed default. | Binding the core directly to any one database or interface. |
| D-011 | Proposed, pending confirmation | Single-user local v1 with manual refresh and a daily schedule while the app or local worker is running. | Continuous monitoring requires a continuously running service. |
| D-012 | Implemented in Stage 1 | Keep `read_at` separate from the `none`/`important`/`excluded` decision on each project paper. A paper may be both read and important. | One exclusive status field would erase one of those facts. |
| D-013 | Implemented in Stage 1 schema | Preserve all source-record-to-snapshot links and record the exact query plan used by each search run. This supports reprocessing and audit trails. | A latest-snapshot pointer or query text alone loses historical evidence. |
| D-014 | Implemented in Stage 1 schema | Use archive timestamps and restrict hard deletion of projects/queries with dependent query history. Audit links use composite keys so providers and queries cannot be crossed. | Cascading deletion or single-column foreign keys would allow loss or misattribution of research history. |
| D-015 | Implemented in Stage 1 | Normalize aware timestamps at the persistence boundary and restore UTC on SQLite reads. | SQLite's native datetime handling discards timezone offsets, which conflicts with domain invariants. |
| D-016 | Implemented in Stage 2, 2026-09-24 | A search page carries all raw HTTP responses used to produce it, a source hit count, and a response index and source database on each record. PubMed needs ESearch plus EFetch per page, while Europe PMC may expose several source families. This preserves auditability without putting HTTP concerns in the domain. | A single raw response would discard PubMed's search evidence; merging Europe PMC IDs without source would risk collisions. |
| D-017 | Implemented in Stage 2, 2026-09-24 | The discovery use case rejects unsupported portable filters and surfaces provider pagination limits/errors. Providers own source syntax, pacing, retry rules, and normalization; none writes to persistence. | Silently dropping a filter or treating a source cap as the end of results would produce misleading discovery runs. |
| D-018 | Implemented in Stage 2, 2026-09-24 | Keep discovery pages and raw source evidence in memory until the Stage 3 audit/merge transaction exists. Do not imply that a provider has durably discovered or deduplicated a paper. | A provider writing directly to the Stage 1 schema would cross application and persistence boundaries and bypass transactional snapshot/outbox handling. |
| D-019 | Implemented in Stage 3, 2026-09-25 | Add immutable snapshot parser version, original source identifier assertions, and per-run observation rows in migration `0002`; keep each response retrieval as a distinct database row even when blob bytes repeat. This makes provenance and classification auditable across runs. | Latest-record pointers, normalized identifiers, and aggregate run counters alone cannot reconstruct an individual source observation. |
| D-020 | Implemented in Stage 3, 2026-09-25 | Resolve exact normalized DOI, PMID, PMCID and provider IDs first. Never merge on title alone; persist conflicts when exact identifiers point to different existing articles. | Aggressive fuzzy matching risks merging distinct research outputs. |
| D-021 | Implemented in Stage 3, 2026-09-25 | Treat newly discovered, new to query, newly published, and metadata updated as separate facts. A configurable 30-day publication window is recorded on each run; incomplete dates yield unknown rather than a false Boolean. | A single “new” flag conflates indexing delay with recent publication and metadata changes. |
| D-022 | Implemented in Stage 3, 2026-09-25 | Declare parser version on each provider, distinct from query translation version. Commit a completed page's database observations, run checkpoint, and outbox events atomically; immutable snapshot bytes may precede the transaction. | Inferring parser version from query translation or committing events after records would weaken reprocessing and delivery guarantees. |
| D-023 | Implemented in Stage 4, 2026-09-25 | Keep `read_at` independent from `important`/`excluded`; derive the four-state display status and allow independent read/unread filtering. Existing project-paper schema suffices. | One exclusive status column would discard whether an important or excluded paper was read. |
| D-024 | Implemented in Stage 4, 2026-09-25 | Add append-only saved-query revisions and bind new runs to the exact portable revision used. Preserve legacy runs with a null revision link and reject concurrent edits before starting a new run. | Updating only the mutable saved query would make historical execution intent ambiguous. |
| D-025 | Implemented in Stage 4, 2026-09-25 | Attach query matches to the owning project idempotently; defer destructive unlinking of project papers and use reversible exclusion for ordinary review views. | Hard unlinking would erase project-specific tags and review history. |
| D-026 | Implemented in Stage 4, 2026-09-25 | Keep project workflows behind an application port; write manual attachment and review-change events in the same transaction as their state changes. Automatic query-match attachment remains a transactional relation without a separate event. | Direct UI-to-ORM operations would couple the desktop client to storage and weaken audit consistency. |
| D-027 | Implemented in Stage 5, 2026-09-25 | Add paper detail and manual-search application contracts before the desktop. Keep PySide6 as a client, compose adapters at startup, and run provider/ingestion I/O off the UI thread. “Delete” archives projects to preserve audit history. | Putting SQL/HTTP and deletion rules in widgets would prevent reuse by FastAPI and risk UI freezes or history loss. |
| D-028 | Implemented in Stage 6, 2026-09-25 | Export committed project paper metadata through a UI-neutral application service to CSV/RIS. Include excluded papers by default and put project review metadata in RIS notes. | Formatting in Qt widgets would block API reuse; silently omitting excluded papers would lose review context. |
| D-029 | Implemented in Stage 6, 2026-09-25 | Persist schedules and execution attempts, enforce one running scheduled attempt per query in the database, and host the runner locally for v1. Keep the scheduler application service Qt-independent for later server workers. Require explicit recovery after crashes rather than expiring a lock while work might still run. | In-memory timers alone lose audit state; automatic lease expiry can permit overlapping workers. |
| D-030 | Implemented in Stage 6, 2026-09-25 | Keep the outbox recording-only. Export reads committed records and scheduling writes direct execution status; neither requires an event consumer. | Adding a broker/consumer now would add infrastructure without a v1 notification or analytics requirement. |
| D-031 | Implemented in Stage 7, 2026-09-25 | Ship migrations with the wheel and locate them in source or installed layouts. Recover interrupted scheduled attempts only with an explicit operator confirmation, atomically failing linked running provider runs. Log safe IDs/states/error type names without raw HTTP exception text. | Source-only migration paths break installed desktop startup; automatic stale-lock expiry may overlap a live worker. |
| D-032 | Implemented in 0.1.1, 2026-09-25 | Scope PubMed identifiers to the current article's direct `PubmedData/ArticleIdList`; reject a contradictory top-level PubMed ID and bump parser provenance. Fail closed on new ingestion when legacy `pubmed-parser-v1` source records exist. Preserve affected 0.1.0 databases as audit archives and rebuild into an empty directory instead of mutating ambiguous canonical/review history automatically. | Recursive XML identifier collection caused false merges; unattended in-place splitting cannot reliably assign old review state and outbox history to the correct papers. |
| D-033 | Implemented in 0.1.2, 2026-09-25 | Add a single opt-in, UI-neutral proxy setting for all PubMed and Europe PMC provider sessions, shared by manual and scheduled searches. Persist it locally, default off, and reject credential-bearing URLs. Explicit direct mode ignores ambient proxy variables. | Widget-owned HTTP configuration would bypass scheduled searches; automatic 403 fallback could unexpectedly change the network route and hide access-policy errors. |
| D-034 | Implemented 2026-09-29 | Add Google Sheets as an optional, one-way project projection behind the application service. Authenticate with an environment-selected local service-account JSON, create a dedicated tab, upsert by canonical paper ID, and mark last success only after writes complete. Sync after eligible scheduled searches or explicit browser action; failures do not rewrite search outcomes. | Uploading private keys to the browser, treating a spreadsheet as canonical storage, and overwriting arbitrary user tabs would weaken security and auditability. |
| D-035 | Approved 2026-09-29 | Prepare the repository for a public GitHub release under MIT, with `Research Scrapper Engine contributors` as the copyright holder. Keep setup, status, limitations, security, and contribution guidance close to the README; distinguish dated acceptance evidence from current operating instructions. | Publishing without a license or with stale release claims would leave users uncertain about rights and safe use. |

## Decision maintenance

When a decision changes, add a dated entry or a new ID rather than silently rewriting its rationale. Update the roadmap and status file at the same time. Recheck provider limits and terms when implementing each provider; the source assessment is time-sensitive.
